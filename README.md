# 工作流优化手册

> 把工业自动化里**能迁移到「AI 办公工作流」**的概念与规范，
> 收拢成一份**可被任何 AI 会话直接读取的判据集**。
>
> 本文件面向**要拿这本手册干活的人**（含开源后的使用者）。

---

## 一、它是什么

工业自动化攒了几十年的方法论（**变更控制、检测设计、防错、节拍与瓶颈**），
**几乎每一条都能平移到「把人的手工动作变成可重复的机器流程」这件事上**。

但这些知识只存在于有工业背景的会话里。**做工作流的会话通常拿不到这套判断框架**，
只能凭通用直觉走 —— 于是重复踩同一类坑。这份手册就是为了让那套判断框架
**自包含、可传递**。

**它和普通"最佳实践清单"的区别**：手册里**每一条都来自一次真实事故**，
而且**每一条都能被一次具体观察证伪**（即能回答"**要发生什么，才说明这条是错的？**"）。
写着"要注意一致性"这类永远为真的建议，一律不收 —— 这也正是它的**收录判据**：
**可迁移 · 有判据 · 有来处（真实事故或实测）· 有反例 · 可证伪**，五条同时满足才收。

## 二、怎么用（最短路径）

**最常见的场景：拿它体检 / 改造一个工作流。顺序不能换** ——
原理 §1-1 说得很直白：**数据源没治好，检查的结论都不可信**。

```
① 按 manual/3-诊断清单.md 四把尺子跑一遍   → 出体检表（§3.5 模板）
② 命中的问号去 manual/1-原理.md 找原理 + 反例
③ 写整改规范前，过 manual/4-规范编写纪律.md §4.2 自检清单
④ 涉及参数/数值的，过 manual/2-引用纪律.md §2.7 自检清单
⑤ 改完用 §3.5 模板最后那一栏做回归检查（必须可复验，不能是"没改坏"这种自我声明）
```

**按你的目标查表**：

| 你要做的事 | 读哪节 |
|---|---|
| **体检一个已有的工作流** | `manual/3-诊断清单.md` —— 四把尺子 × 40 问，逐问给"怎么查" |
| **想搞清某条判据为什么成立** | `manual/1-原理.md` —— 十三条，每条含判据 / 操作 / 反例 |
| **要写一条给别人执行的规范** | `manual/4-规范编写纪律.md` —— 十二条要求 + 自检清单 |
| **要写下一个数值或结论** | `manual/2-引用纪律.md` —— 它管"这个结论凭什么算数" |
| **要判断某条规范该不该加** | `manual/6-元规则.md` —— 不设多份 / 判据可证伪 / 不追求越来越全 |
| **只想快速查一条** | `references/index.md` —— 十三条一行版 / 四把尺子 / 写规范七问 |
| **要按值全仓找副本** | `scripts/find_copies.py`（用法见 `SKILL.md` §三） |

> 🔴 **只做①③不做②④，会得到"看起来很专业但没人能照做"的指南** ——
> 这正是本手册诞生的原因：上一版指南的诊断是准的，但它自己变成了 4 份手抄本、
> 修订只落一份、通则三处各写。**它防住了被改造对象的病，没治自己的病。**

  │   ├── 4-规范编写纪律.md     十二条要求 + 自检清单

> **§5 失效模式库不含在本分发包内。** 真实案例另存（含具体项目线索），
> 手册只收**通用条目**，案例库反向引用手册的条目编号。
> 这样手册可独立开源，案例库保持私有 —— **两库单向依赖，不需要互相同步。**

### 十三条原理一览

**第一层 · 数据源**：1 单一数据源 · 2 变更闭环 · 8 指针必须可执行 · 11 对账以证据为准
**第二层 · 检测**：3 预防优于探测 · 4 先问绿灯判的是什么 · 5 未执行≠通过 ·
10 硬失败要在产出之前 · 12 验收要判到要考的东西
**第三层 · 决策与推广**：6 先问数值能不能测 · 7 标准件优先 · 9 对账同源 · 13 规则要写明奖励什么行为

> 🔴 **其中 5、6、10、12、13 是实战新增的** —— 它们不在最初的六条里，
> 是手册按自己的判据跑了一遍之后才发现的缺口。
> **一份没被自己的判据考过的手册，不值得信。**

## 四、五条红线（不论读没读手册都遵守）

1. **来源的身份不是证据。**「新 / 活 / 大 / 权威 / 多处在写」**全部无效**，
   能被**命令与输出**支持的才算。有分歧时**跑一次真的**，别比谁更新。
2. **未执行 ≠ 通过。** 任何检查项"没真跑"时，总判定**必须降级并自述覆盖面**。
3. **填不出证据，就不要往下写。** 凡写「新值 / 校正值 / 以某版为准」，必须填满证据栏。
4. **同一条文字只许出现一处，其余留指针**（指针必须**可执行**）。
5. **任何加法之前先问："这条规则奖励什么行为？"** 最短通过路径若是你想要的反面，这条规则在教你做错事。

（完整表述与实测反例见 `SKILL.md` §二 与 `manual/1-原理.md`。）

## 五、🔴 评估与修改建议分工（用这本手册改东西时，先读这一节）

> **这是本手册最容易违反、代价最贵的一条使用方法。**
> 它不只针对"改手册"，**改任何流程 / 规范都适用**。

**发起评估的会话，不要亲自执行修改。**

| 角色 | 会话 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **📋 评估方** | **独立会话**（不参与日常执行） | 读现状 → **出评估报告** | 🔴 **不改任何文件** |
| **🔧 执行/维护方** | **项目会话**（熟悉该对象的会话） | 读报告 → **结合自己的上下文** → 裁定改不改、怎么改 → 执行 | **不能只照抄报告** |

**为什么建议分开 —— 只有一条理由**：
**改的人如果同时是判的人，他会无意识地保住自己写的东西。**

- **评估方没有历史包袱** —— 它不记得"当初为什么这么写"，所以能看出执行方**看不见的缺口**。
- **执行方有上下文** —— 它知道某条判据为什么这么写、哪些坑已踩过。
  评估方的报告是**材料**，不是**命令**。
- 一句话：**评估方负责"看出问题"，执行方负责"判断这个问题成不成立、值不值得改"。**
  **两者判据来源不同，缺一个都不行。**

### 评估方怎么写报告

1. **只读** —— 全程不改文件，产出就是**一份报告**，交给执行方。
2. **每条结论要能回溯** —— 标具体条目编号、给可复跑的命令与输出。**不许虚构现状**。
3. 🔴 **把"缺"和"错"分开写** —— 缺口不一定是错误。评估方换的尺子不同，
   量出的"缺"可能恰恰是**对象有意不做的事**（例：用 SOP 尺子量一本面向机器流程的手册，
   量出"零责任人"—— 但那本就不需要交代人）。
4. **列出"待确认项"** —— 哪些结论需要执行方结合上下文才能裁定。
5. 报告开头标：**「本文为评估意见，非改动。任何改动需单独确认。」**

### 执行方拿到报告之后

1. **先裁定，再动手** —— 逐条决定 采纳 / 不采纳 / 暂不处理，并写下**理由**。
2. 🔴 **绝不做"照单全收"** —— 评估方看不到执行方的上下文，其建议可能违反已有设计。
3. **改完做回归检查**（见 §二 第⑤步），**不能是"没改坏"这种自我声明**。

> 📌 **这条纪律本身有实证**：本项目跑过两次独立评估 —— 一次考出"**声称的能力实际不存在**"
> （删了脚本没删声称，执行方自己没发现），一次考出"**只有异常检测、没有异常处置**"。
> **两次都证明：评估方的视角差 ＝ 它的价值；执行方的裁定 ＝ 防止改错的那道闸。**

## 六、适用范围与边界（诚实标注）

- 手册的判据来源仍限于**一次改造 + 三个项目**。**换个场景它可能不成立** ——
  用它时优先信你自己的实测，发现判据管不到就记一笔。
- 🔴 **别把它当 SOP 用。** 它是"**检测装置**"，不是"**作业标准**"。
  它**不写责任人、不写交接与升级路径**（面向机器流程的有意取舍）。
  要落地成人执行的 SOP，需要用 SOP 补"角色 / 交接 / 升级"，
  用手册补"检查点 / 变更控制" —— 两者互补，不重叠。
- `manual/2-引用纪律.md` §2.4 的**必填模板尚未被实战检验** ——
  真正挡住错值的是"判定类只留指针"这个**结构**，不是模板本身。

## 七、常见坑（下面每一条都在中文 Windows 上实测踩过）

### 1. 重定向输出时会崩（已修）

```
UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f534'
```

**原因**：中文 Windows 下管道默认 GBK，而输出里有 `✅` `🔴` `🛑`。而**重定向正是挂 CI 的标准用法**。

**现在**：脚本启动时对 stdout/stderr 做了 `reconfigure(errors="replace")`，不崩了，个别符号会变 `?`。

> ⚠️ **不要把编码改成 UTF-8 来"修"它** —— 换了编码，中文在 GBK 终端里会整段乱码。
> `errors="replace"` 只牺牲个别符号，这是有意的取舍。

### 2. 🔴 `--value` 别写带前导斜杠的值（Git Bash / MSYS）

**症状**：`0 处命中`、退出码 `0`、结尾还打「✅ 没有未标注命中」—— **看起来全绿，其实一条都没查。**

**原因**：MSYS 把以斜杠开头的参数值当成绝对路径，改写成本机安装目录：

```
--value "/archive/"   →  'D:/.../PortableGit/archive/'
```

参数永远匹配不上，**而且不报错**。

**现在**：脚本检测到"形如绝对路径 + 0 命中"会打 `⚠` 并把结论降级（**不再给 ✅**）。
但它**猜不出你原本想搜什么** —— 护栏只能提醒，不能替你纠正。

**修法**：命令前加 `MSYS_NO_PATHCONV=1`，或写成 `archive/`（不带前导斜杠）。
**自查真值**：

```bash
python -c "import sys;[print(repr(a)) for a in sys.argv[1:]]" --value /archive/
```

### 3. 日记会被当成"活文档"（已修）

**症状**：`memory/2026-10-17.md` 被判成「未标注的现在时声明」，提示你去改历史记录 ——
而脚本自己另一行又写着"日记不要动"。

**原因（旧版）**：`RE_DIARY` 要求 `memory` 前面有一个斜杠，而 `relpath` 对**根目录的直接子目录**
返回 `memory\x.md`（前面没有斜杠）⇒ **当 `memory` 恰好是扫描根目录的直接子目录时**，
`[D]` 这一类永远命不中（更深的路径如 `docs/memory/` 反而是正常的）。

### 4. 真实项目上一定会有假阳性，别照单全改

`修改日志.md`、`变更记录.md`、`CHANGELOG.md` 这类**历史文档**，按路径看就是活文档 `[B]`，会被全部标红。

**分类是按路径猜的启发式**，脚本最后一行自己也这么写。作者实测：某真实项目 23 处命中里 20 处是 `[B]`，
其中大半是历史文档。**结论要人看，不要机器看。**

### 5. 崩溃和"有命中"共用退出码 1

`exit 1` 既是"有未标注命中"，也是 Python 未捕获异常的默认退出码。
**要用退出码判成败，先确认 stderr 里没有 traceback。**

## 八、自检（可复制，作者已逐条实跑）

```bash
# 1) 基本可用（3 个退出码：0 干净 / 1 有命中 / 2 参数错）
python scripts/find_copies.py --root . --value "单一数据源"; echo "exit=$?"

# 2) 中文 Windows 下重定向不崩（不应出现 Traceback）
PYTHONIOENCODING=gbk python scripts/find_copies.py --root . --value "单一数据源" > /dev/null; echo "exit=$?"

# 3) 斜杠值护栏（Git Bash / MSYS 下应出现 ⚠ 降级提示）
python scripts/find_copies.py --root . --value "/archive/"

# 4) 只读性：跑完不应有任何文件被写（前后比对，别用时间窗——你自己刚编辑过的文件也会被算进去）
find . -type f -exec stat -c '%n %Y' {} \; | sort > /tmp/mt_before.txt
python scripts/find_copies.py --root . --value "单一数据源" > /dev/null
find . -type f -exec stat -c '%n %Y' {} \; | sort > /tmp/mt_after.txt
diff /tmp/mt_before.txt /tmp/mt_after.txt && echo "只读 OK"
```

> **装成 agent skill**：`SKILL.md` 的 `name` 是 `workflow-optimization`（小写字母 + 连字符，
> 符合常见加载器的命名要求）。建议目录也用同名 —— 本仓库发布时就是这么放的。
